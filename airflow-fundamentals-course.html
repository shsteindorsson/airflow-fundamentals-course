Airflow Fundamentals: A Hands-On ETL Course

Written for Airflow 3.4.0 and Python 3.14, November 2026. You write the code and the tests; the course gives you specs, signatures and checkpoints.

extract› parse› transform› load

How to use this course

You will build one real pipeline, weather_etl, over ten modules: extract hourly weather from the free Open-Meteo API, parse the raw JSON into validated records, transform them into daily summaries, and load them into Postgres. No API key is needed; a keyed API is a stretch goal in Module 9.

The course gives you specs, function signatures, acceptance criteria and hints. You write the implementation and the tests. Only Airflow boilerplate you cannot reasonably guess is shown in full.

Budget: roughly 15 to 20 hours. Each module ends with a checkpoint; do not move on until it passes.

Prerequisites: comfortable with Python functions, dicts and lists; basic terminal use; Docker installed (for Postgres only). Windows users need WSL2.

Ground rules that make you better at Python:

  • Keep business logic in plain Python modules under src/. DAG files only wire tasks together. This is what makes the code testable without Airflow running.
  • Write the test before or alongside each function, never after the whole module is done.
  • Use type hints everywhere and run ruff and mypy before each checkpoint.
  • When stuck, read the official docs page linked in the module before searching elsewhere.

The pipeline you will build:

  1. extract — call the API for one day and save the raw response to disk, untouched.
  2. parse — read the raw file, validate its shape, and turn parallel arrays into typed records.
  3. transform — aggregate hourly records into one daily summary per city.
  4. load — upsert the summaries into Postgres so reruns never create duplicates.

Module 0: Local setup (about 1 hour)

You will run Airflow 3.4.0, the current stable release, with airflow standalone in a uv virtual environment, plus Postgres in Docker as the load target. Standalone runs the scheduler, Dag processor, triggerer and API server together on SQLite, which is right for local development (Quick Start).

Use Python 3.14. Airflow 3.4 supports Python 3.10 to 3.14 and publishes a constraints file for 3.14, so every pinned dependency below installs cleanly on it. Python 3.12 and 3.13 also work if you already have them.

Install

source .venv/bin/activate

AIRFLOW_VERSION=3.4.0
PYTHON_VERSION="$(python -c 'import sys; print(f"{sys.version_info.major}.{sys.version_info.minor}")')"
CONSTRAINT_URL="https://raw.githubusercontent.com/apache/airflow/constraints-${AIRFLOW_VERSION}/constraints-${PYTHON_VERSION}.txt"

The constraints file pins every dependency to versions tested with that release. Always pass it, including when installing your own package.

Exercise 0.1: write pyproject.toml

Write it yourself using the packaging guide. Requirements:

  • Package name weather, source in src/ (the “src layout”), build backend of your choice (hatchling is simplest).
  • Runtime dependency: requests.
  • An optional dev group: pytest, ruff, mypy, types-requests.
  • A [tool.pytest.ini_options] section with testpaths = ["tests"].
  • A [tool.ruff.lint] section that selects at least E, F, I, B and AIR. The AIR rules catch Airflow-specific mistakes such as removed Airflow 2 imports.

Why editable install (-e)? Airflow imports your Dag file, which imports weather.extract. The package must be importable from the same environment Airflow runs in.

Exercise 0.2: env.sh and Postgres

env.sh keeps Airflow’s state inside the project and points it at your Dags:

export AIRFLOW_HOME="$PWD/.airflow"
export AIRFLOW__CORE__DAGS_FOLDER="$PWD/dags"
export AIRFLOW__CORE__LOAD_EXAMPLES=False
export AIRFLOW_CONN_WEATHER_DB='postgres://weather:weather@localhost:5433/weather'
export WEATHER_DATA_DIR="$PWD/data"

Any AIRFLOW__SECTION__KEY variable overrides airflow.cfg, and any AIRFLOW_CONN_<ID> variable defines a connection without touching the database. Source this file in every terminal you use: a terminal without it gets a different AIRFLOW_HOME, database and password.

Write docker-compose.yml yourself: one service, image postgres:17, user, password and database all weather, host port 5433 mapped to 5432 (avoids clashing with a local Postgres), and a named volume. Add a healthcheck using pg_isready.

Checkpoint 0

Module 1: The mental model (about 1 hour)

Airflow does not move your data; it decides when your Python runs, in what order, and what happens on failure. Everything else follows from that.

Term What it is Why it matters for this course
Dag A Python-defined graph of tasks plus a schedule weather_etl is one Dag with four tasks
Task One node in the graph; created by an operator or a @task function Each ETL stage is one task
Dag run One execution of the Dag for one data interval One run = one day of weather
Task instance One task within one Dag run; has a state and logs What you retry and inspect
Data interval The time window a run is responsible for Decides which day you fetch, not the wall clock
XCom Small values passed between tasks, stored by Airflow Pass file paths, never datasets
Connection Credentials and host for an external system How load finds Postgres
Variable A key-value setting stored in Airflow Optional config, read inside tasks only

Three rules the rest of the course enforces:

  1. Dag files are parsed constantly. The Dag processor re-runs your Dag file’s top-level code every few seconds. Never call an API, query a database or read a Variable at the top level (Best Practices).
  2. Tasks must be idempotent. Running the same task for the same interval twice must give the same result. Use upserts, not inserts, and derive dates from the data interval, never from now().
  3. Tasks should not share memory or local state. Each task may run in a different process or machine. Hand off through durable storage and pass only the location through XCom.

In Airflow 3, import authoring APIs from airflow.sdk (dag, task, DAG, Variable, Connection). Older tutorials using airflow.decorators or airflow.models are Airflow 2 and will mislead you.

With airflow standalone all of these run from one terminal; in production each is a separate process or container. Your task code runs only on the worker, while the Dag processor re-runs your file’s top level constantly, which is why that top level must stay cheap.

  • What does catchup do, and what is its default in Airflow 3?

Checkpoint 1

Module 2: Your first Dag with TaskFlow (about 1.5 hours)

The TaskFlow API turns plain functions into tasks: decorate them with @task, call them inside a @dag function, and Airflow infers the dependencies and the XCom hand-offs from the return values (TaskFlow tutorial). This is the only shape you need to see in full:

import pendulum
from airflow.sdk import dag, task


@dag(
    schedule=None,                     # manual runs only, for now
    start_date=pendulum.datetime(2026, 11, 1, tz="UTC"),
    catchup=False,
    tags=["course"],
)
def hello_taskflow():
    @task
    def make_numbers() -> list[int]:
        ...

    # more tasks here

    numbers = make_numbers()           # returns a reference, not the list
    # chain calls: report(square_all(numbers))


hello_taskflow()                       # registers the Dag; easy to forget

Exercise 2.1: build hello_taskflow

In dags/hello_taskflow.py, write three tasks:

  • make_numbers returns [1, 2, ..., 10].
  • square_all(numbers) returns the squares.
  • report(squares) logs the sum and the run’s data_interval_start. Get the latter by adding a keyword parameter named data_interval_start=None; Airflow injects context values that match parameter names.

Use the standard logging module, not print, so output lands cleanly in task logs.

Exercise 2.2: run it three ways

  1. python dags/hello_taskflow.py — the loader test. No output and no error means it parses.
  2. airflow dags test hello_taskflow 2026-11-01 — runs the whole Dag in one process, no scheduler needed. Your fastest feedback loop.
  3. In the UI, unpause and trigger it. Open each task’s logs and its XCom tab.

Exercise 2.3: break it on purpose

  • Make square_all raise on its first attempt only. Hint: the context value ti has a try_number. Set retries=2 and retry_delay=pendulum.duration(seconds=10) on the task and watch it recover in the UI.
  • Put logging.warning("parsed!") at the top level of the file. Watch the scheduler output in the standalone terminal and count how often it appears. Then remove it; this is rule 1 from Module 1.
  • Return a set from make_numbers. Read the error. XCom values must be serializable; learn what that means here rather than in Module 3.

Checkpoint 2

Module 3: Extract (about 2.5 hours)

The extract task fetches one day of hourly weather per city and writes each response to disk byte for byte, before any parsing. Keeping the raw file means a parsing bug never forces you to call the API again, and you can always prove what the source sent.

API: the Open-Meteo Historical Weather API, https://archive-api.open-meteo.com/v1/archive. No key; free for non-commercial use, so keep backfills modest. Read its docs page once before coding.

Exercise 3.1: grab a real fixture first

Before writing code, call the API by hand and save the result as a test fixture:

curl "https://archive-api.open-meteo.com/v1/archive?latitude=59.91&longitude=10.75&start_date=2026-10-01&end_date=2026-10-01&hourly=temperature_2m,precipitation,wind_speed_10m,relative_humidity_2m&timezone=UTC" \
  > tests/fixtures/oslo_2026-10-01.json

Open it. Note that hourly holds parallel arrays: one time list and one list per variable, aligned by index. Turning that into rows is the parse step’s job. Then call it again with a bad variable name and save that response too as tests/fixtures/error_bad_variable.json; it shows you the API’s error format.

Exercise 3.2: config.py and models.py

  • In models.py, a frozen dataclass City with slug: str, name: str, latitude: float, longitude: float. Use @dataclass(frozen=True, slots=True) and find out what each option does.
  • In config.py: CITIES, a tuple of three City values (for example Oslo, Berlin, Madrid); ARCHIVE_URL; HOURLY_VARIABLES as a tuple of the four variable names above; and a function data_dir() -> Path that reads WEATHER_DATA_DIR and raises a clear error if it is unset.

Exercise 3.3: extract.py

Implement these, keeping the module free of Airflow imports:

class PermanentAPIError(Exception): ...        # 4xx: retrying will not help

class HttpGetter(Protocol):                     # anything with a requests-like .get()
    def get(self, url: str, *, params: Mapping[str, Any], timeout: float) -> Response: ...

def build_params(city: City, day: date) -> dict[str, str | float]: ...
def raw_path(base: Path, city: City, day: date) -> Path: ...
def fetch_day(city: City, day: date, http: HttpGetter, timeout: float = 30.0) -> str: ...
def write_atomic(text: str, path: Path) -> Path: ...
def extract_day(day: date, cities: Sequence[City], base: Path, http: HttpGetter) -> list[Path]: ...

Acceptance criteria:

  • build_params requests one day (start_date == end_date), all HOURLY_VARIABLES comma-joined, and timezone=UTC.
  • raw_path returns a partitioned path: base/raw/open_meteo/date=2026-10-01/oslo.json. Partitioning by date is what makes reruns overwrite instead of duplicate.
  • fetch_day returns response.text untouched. On a 4xx it raises PermanentAPIError whose message includes the API’s reason field. On a 5xx or timeout it lets a requests exception propagate, so Airflow’s retries handle it.
  • write_atomic writes to a temporary file in the same directory, then renames it into place with Path.replace. A crash mid-write must never leave a half-written file at the final path.
  • extract_day creates directories as needed and returns the written paths.

Why a Protocol and an injected http argument? Your tests can pass a tiny fake object instead of patching requests. This is dependency injection, and it is the single most useful testing habit to build.

Exercise 3.4: tests in tests/test_extract.py

Write a FakeHttp class in tests/conftest.py that records each call and returns canned responses. Then write at least these tests:

  • build_params produces the expected dict for one city and day.
  • raw_path produces the partitioned path (use pytest’s tmp_path fixture as base).
  • fetch_day returns the fixture text unchanged on 200.
  • fetch_day raises PermanentAPIError mentioning the reason on 400, using your error fixture.
  • fetch_day raises requests.HTTPError on 503.
  • Running extract_day twice for the same day leaves exactly one file per city.
  • write_atomic leaves no file at the target if writing fails. Hint: monkeypatch a method so it raises.

Use @pytest.mark.parametrize for the status-code cases instead of copy-pasting tests.

Exercise 3.5: the extract task

Create dags/weather_etl.py with schedule=None for now and a single extract task. It takes data_interval_start, derives the day, calls extract_day with a real requests.Session(), and returns the paths as a list of strings. Import weather.extract inside the task function, not at the top of the file, to keep parsing fast.

A 4xx should fail the task immediately without retries. Find the Airflow exception that does that, AirflowFailException, and its Airflow 3 import path in the docs; catch PermanentAPIError in the task and re-raise it as that.

One real-world wrinkle: the archive lags real time by several days, so the most recent days may come back with null values. Do not handle it here. The parse step will.

Checkpoint 3

Module 4: Parse (about 2.5 hours)

The parse task turns an untrusted raw response into typed, validated records, and fails loudly when the source changes shape. In production most pipeline incidents start here: a renamed field, a changed unit, a missing hour. Your parser’s job is to notice before bad data reaches the database.

Exercise 4.1: the record type

In models.py, add a frozen dataclass HourlyObservation:

city: str
observed_at: datetime          # timezone-aware, UTC
temperature_c: float | None
precipitation_mm: float | None
wind_speed_kmh: float | None
relative_humidity_pct: float | None

Give it two methods: to_json() -> str and a @classmethod from_json(line: str) -> HourlyObservation. datetime is not JSON-serializable, so you must decide how to encode it (ISO 8601 strings) and decode it.

Exercise 4.2: parse.py

class ParseError(ValueError): ...           # the source is malformed: fail, do not retry
class SourceNotReady(Exception): ...        # the day exists but has no data yet: retry later

EXPECTED_UNITS: dict[str, str] = {...}      # fill in from your fixture's hourly_units

def parse_payload(payload: Mapping[str, Any], city: str, day: date) -> list[HourlyObservation]: ...
def parse_file(path: Path, city: str, day: date) -> list[HourlyObservation]: ...
def staged_path(base: Path, city: str, day: date) -> Path: ...  # base/staged/hourly/date=.../oslo.jsonl
def write_jsonl(records: Iterable[HourlyObservation], path: Path) -> Path: ...
def read_jsonl(path: Path) -> list[HourlyObservation]: ...

parse_payload must enforce every rule below, each with an error message that names the field and the problem:

  1. hourly and hourly_units exist and are dicts.
  2. Every variable in HOURLY_VARIABLES is present in both.
  3. Every unit matches EXPECTED_UNITS. A silent switch from °C to °F is exactly the drift you want to catch.
  4. Every array has the same length as time.
  5. Timestamps parse, are unique, all fall on day, and there are exactly 24.
  6. Every value is an int, a float or None. Watch out: isinstance(True, int) is True in Python, so booleans need an explicit check.
  7. If every value of every variable is None, raise SourceNotReady. Some None values are allowed and stay None.

The core transformation is zipping parallel arrays into rows. Try writing it first with zip(..., strict=True) and think about why strict=True matters here.

Map the API’s variable names to your field names in one dict, not in scattered if statements.

Exercise 4.3: tests in tests/test_parse.py

Add a fixture in conftest.py that loads the Oslo JSON fresh for every test, so a test can mutate it without affecting others. Then write tests for:

  • The happy path: 24 records, the first record matches index 0 of each fixture array, and observed_at is UTC-aware.
  • One test per rule 1 to 6, each mutating the fixture to break exactly one rule and asserting ParseError with pytest.raises(ParseError, match=...).
  • A few None values survive as None; all None raises SourceNotReady.
  • to_json then from_json returns an equal object. Then the same round trip through write_jsonl and read_jsonl.

If writing a test is awkward, your function is probably doing too much. Split it and test the pieces.

Exercise 4.4: the parse task

Add a parse task that receives the extract task’s list of raw paths, works out each city from the file name, parses it, writes the staged JSONL file, and returns the staged paths. Wire it as parse(extract()).

Map your exceptions to Airflow behaviour in the task, not in parse.py: ParseError fails immediately without retries, and SourceNotReady is allowed to propagate so the task’s normal retries apply. Module 8 tunes those retries.

Checkpoint 4

Module 5: Transform (about 1.5 hours)

The transform task aggregates 24 hourly records per city into one DailySummary row per city, using pure functions with no I/O in the core logic. Pure functions are the easiest code in the whole pipeline to test, so this module is where you practise writing precise tests.

Exercise 5.1: the summary type

Add a frozen dataclass DailySummary to models.py:

city: str
day: date
temp_min_c: float | None
temp_max_c: float | None
temp_mean_c: float | None
precipitation_total_mm: float | None
wind_max_kmh: float | None
humidity_mean_pct: float | None
hours_observed: int        # hours with a non-null temperature
is_complete: bool          # all 24 hours present for every variable

Add to_json and from_json as before. Notice the duplication with HourlyObservation; Module 9 offers a refactor.

Exercise 5.2: transform.py

def summarize(records: Sequence[HourlyObservation]) -> DailySummary: ...
def summarize_all(records: Iterable[HourlyObservation]) -> list[DailySummary]: ...
def curated_path(base: Path, day: date) -> Path: ...   # base/curated/daily/date=.../summary.jsonl

Rules:

  • summarize raises ValueError on an empty input or on records from more than one city or day.
  • None values are ignored in every aggregate. If a variable has no values at all, its aggregate is None, not 0.
  • Round floats to 2 decimals at the end, not in intermediate steps.
  • summarize_all groups by city and returns summaries sorted by city slug.

Write the grouping twice: once with collections.defaultdict(list) and once with itertools.groupby. The second one has a trap: it only groups adjacent items. Find it with a test, then keep whichever version you find clearer. statistics.fmean is handy for means.

Exercise 5.3: tests in tests/test_transform.py

Build small inputs by hand rather than using the API fixture, so every expected number is obvious. A helper make_obs(hour, temp=..., precip=...) with defaults keeps tests short.

  • Temperatures 1.0, 2.0, None give min 1.0, max 2.0, mean 1.5 and hours_observed == 2. Compare floats with pytest.approx.
  • Precipitation all None gives None, not 0.0.
  • 24 complete hours give is_complete is True; 23 give False.
  • Mixed cities raise ValueError; so does an empty list.
  • summarize_all on interleaved cities (Oslo, Berlin, Oslo, …) returns one correct summary per city. This is the test that catches the groupby trap.
  • Run summarize on the parsed Oslo fixture and check temp_min_c <= temp_mean_c <= temp_max_c.

Optional: install hypothesis and write one property-based test asserting that min ≤ mean ≤ max for any list of non-null temperatures.

Exercise 5.4: the transform task

The transform task reads all staged JSONL files for the run’s day, calls summarize_all, writes one curated JSONL file, and returns its path. Wire it as transform(parse(extract())).

Checkpoint 5

Module 6: Load (about 2 hours)

The load task upserts the daily summaries into Postgres through an Airflow Connection, so rerunning any day replaces its rows instead of duplicating them. You also meet your first classic operator, mixed with TaskFlow tasks in the same Dag.

Exercise 6.1: the table

Write sql/create_tables.sql yourself. Requirements: a table daily_weather with one column per DailySummary field, numeric(6,2) for measurements, a loaded_at timestamptz defaulting to now(), and a primary key on (city, day). Use CREATE TABLE IF NOT EXISTS so the statement is idempotent.

Run it from the Dag with SQLExecuteQueryOperator from airflow.providers.common.sql.operators.sql, passing conn_id="weather_db" and sql="create_tables.sql". For Airflow to find that file, set template_searchpath on the @dag decorator to the absolute path of your sql/ folder. Look up why that parameter is needed: sql is a templated field.

Exercise 6.2: load.py

Keep it free of Airflow imports. It works with any DB-API connection, which is what PostgresHook.get_conn() returns.

COLUMNS: tuple[str, ...] = (...)            # same order everywhere

def summary_to_row(s: DailySummary) -> tuple[Any, ...]: ...
def build_upsert_sql(table: str = "daily_weather") -> str: ...
def upsert_summaries(conn: DbApiConnection, summaries: Sequence[DailySummary]) -> int: ...

Rules:

  • build_upsert_sql produces INSERT ... ON CONFLICT (city, day) DO UPDATE SET col = EXCLUDED.col, ... for every non-key column, plus loaded_at = now(). Generate the column lists from COLUMNS rather than typing them twice.
  • Values go in as query parameters (%s placeholders), never formatted into the string. Only the table name, which you control, is interpolated.
  • upsert_summaries runs all rows in one transaction with cursor.executemany: commit at the end, roll back and re-raise on any error. It returns the number of rows sent.
  • Define DbApiConnection as a small Protocol with cursor(), commit() and rollback().

Exercise 6.3: tests

Unit tests in tests/test_load.py, no database needed:

  • summary_to_row returns values in COLUMNS order.
  • build_upsert_sql contains one %s per column, the ON CONFLICT (city, day) clause, and does not update city or day.
  • With a fake connection, upsert_summaries commits once on success, and rolls back and re-raises when the fake cursor raises.

Integration tests in tests/test_load_integration.py against the Docker Postgres:

  • Mark them with @pytest.mark.integration and register the marker in pyproject.toml. Skip them unless an environment variable such as WEATHER_TEST_DSN is set; pytest.mark.skipif does this.
  • Find out which Postgres driver the provider installed (uv pip list | grep -i psycopg) and connect with it directly in a fixture that creates the table and truncates it after each test.
  • Upserting the same three summaries twice leaves exactly three rows; upserting a changed value updates it.
  • A batch with one invalid row (for example a 300-character city) leaves the table unchanged.

Run them with pytest -m integration.

Exercise 6.4: the load task

The load task reads the curated file, opens a connection with PostgresHook(postgres_conn_id="weather_db"), calls upsert_summaries, and returns the row count. Import the hook inside the task. Wire the full chain so create_tables runs before extract: create_tables >> extracted, where extracted = extract().

Exercise 6.5: a verification task

Add a final verify task that queries daily_weather for the run’s day using hook.get_first(...) and fails if the row count differs from len(CITIES). A pipeline that checks its own output is worth more than one that only reports success.

Checkpoint 6

Module 7: Testing the Dag (about 2 hours)

Your logic is already tested; this module tests the Dag as a whole and organizes the suite so it runs in seconds. Aim for many fast unit tests, a few integration tests, and one end-to-end run.

Layer What it proves Needs Run with
Unit Each function behaves (Modules 3 to 6) Nothing pytest
Dag integrity The Dag file imports and follows your rules Airflow installed pytest
Dag structure Tasks and dependencies are what you intended Airflow installed pytest
Integration SQL works against real Postgres Docker Postgres pytest -m integration
End-to-end A full run produces correct rows Postgres, network, metadata DB pytest -m e2e or airflow dags test

Exercise 7.1: Dag integrity tests

In tests/test_dag_integrity.py, load your Dags with DagBag from airflow.dag_processing.dagbag (Testing a Dag), passing your dags/ folder and include_examples=False. Use a module-scoped fixture so it loads once. Assert:

  • dagbag.import_errors == {}. Print the errors in the assertion message so failures are readable.
  • weather_etl exists.
  • Every Dag has at least one tag, catchup set explicitly, and retries >= 1 in its default args.

These tests need AIRFLOW_HOME and friends. Set them for the test session in conftest.py using monkeypatch-style environment setup or the pytest-env plugin, pointing at a throwaway directory so tests never touch your real .airflow.

Exercise 7.2: structure test

Assert the exact graph with a dict of task id to downstream task ids, for example {"create_tables": {"extract"}, "extract": {"parse"}, ...}, comparing against dag.get_task(task_id).downstream_task_ids. This catches a dependency deleted by accident during a refactor.

Exercise 7.3: prove there are no side effects at parse time

Write a test that monkeypatches requests.Session.request to raise, then imports the Dag file through DagBag. If it imports cleanly, the Dag file makes no network calls at parse time. This turns rule 1 from Module 1 into an executable check.

Exercise 7.4: test the tasks’ Airflow glue

Your task functions contain a little glue: exception mapping, date derivation, path handling. Test it by calling the underlying Python function directly. Each @task object exposes the original function; find the attribute name in the TaskFlow docs or with dir(). Mock the hook by setting AIRFLOW_CONN_WEATHER_DB with unittest.mock.patch.dict("os.environ", ...), as the Best Practices page shows.

Exercise 7.5: end-to-end, and a mutation drill

  • Add one @pytest.mark.e2e test that calls weather_etl.test(logical_date=...) for a fixed past day and then queries Postgres for three rows. Skip it unless an environment variable is set.
  • Mutation drill: introduce five small bugs by hand, one at a time (flip < to <=, drop strict=True, remove the rollback, swap two columns in COLUMNS, use now() for the date). Run the suite after each. Any bug that survives means a missing test; write it.

Exercise 7.6: one command to check everything

Write scripts/check.sh that runs ruff check, ruff format --check, mypy src, and pytest -m "not integration and not e2e", and exits non-zero on the first failure (set -euo pipefail). Run it before every commit.

Checkpoint 7

Module 8: Scheduling, backfills and retries (about 2.5 hours)

Your Dag now runs itself every day, loads history with a backfill, waits for late data instead of failing, and triggers a second Dag when new data lands. This is where the idempotency work from earlier modules pays off.

Exercise 8.1: put it on a schedule

Change weather_etl to schedule="@daily", a fixed start_date in the past (for example 1 September 2026, UTC), catchup=False and max_active_runs=3 to stay gentle on a free API. Move retry settings into default_args: retries=3, retry_delay of 5 minutes, and retry_exponential_backoff=True. Unpause it and check in the UI which data interval the next run covers.

Exercise 8.2: backfill a month

airflow backfill create --dag-id weather_etl --from-date 2026-09-01 --to-date 2026-09-30

Watch runs proceed three at a time. Then answer in NOTES.md: how many rows does daily_weather have now, and what would happen if you ran the same backfill again? Run it again to check. If the count changed, an earlier module has an idempotency bug; find it.

Exercise 8.3: find the retry bug

Trigger a run for a very recent day, where the archive still returns null. Parse raises SourceNotReady and Airflow retries it. Explain in NOTES.md why retrying parse can never succeed in this design. (Hint: what does parse read, and when was it written?)

The fix is a sensor: a task that waits until a condition is true. Add a wait_for_data task before extract using the @task.sensor decorator with mode="reschedule", a poke_interval of one hour and a timeout of seven days. It calls a small is_day_available(city, day, http) -> bool function you add to extract.py and test like the others. In reschedule mode the sensor frees its worker slot between checks instead of sleeping in it; read the Sensors page to see why that matters at scale.

After this change, SourceNotReady reaching parse signals a real anomaly, so map it to an immediate failure too.

Exercise 8.4: break and recover

Practise the operations you will do in real incidents, each in the UI:

  • Stop Postgres (docker compose stop), let a run fail at load, start it again, and clear only the failed task. Extract and parse must not rerun.
  • Clear a successful run’s extract with downstream tasks included and confirm the row count is unchanged.
  • Add an on_failure_callback to default_args that logs a one-line summary (Dag id, task id, logical date, exception). In production this is where an alert would go.

Exercise 8.5: data-aware scheduling with Assets

Declare daily_weather = Asset(name="daily_weather") (import Asset from airflow.sdk) in a small shared module, and add it as an outlet on the load task. Then write a second Dag, weather_report, with schedule=[daily_weather]. Its one task queries the last 7 days per city and logs the warmest and wettest day. It runs only when load succeeds, with no time-based schedule at all. Add it to your integrity and structure tests.
